# First import implementation plan

Status: stages 1–2 implemented as read-only preview; stages 3–5 planned. Tracks issue #15 against [the reuse design](2026-10-22-project-packs-design.md) and [MVP](mvp.md).

## Shape of the journey

One guided flow with two read-only MCP tools now and one writing tool later. Existing `discover_assets`, `search`, and `read` stay unchanged.

| Step | Tool | Engine (deterministic) | Coding client (advisory) |
| --- | --- | --- | --- |
| 1. Inspect | `list_import_candidates` | Classify source assets, summarize stack evidence for both projects | Recommend relevant candidates with evidence; user selects |
| 2. Plan | `plan_import` | Collect bundles, map destinations, check paths/collisions, find machine paths and likely secrets, list adaptation sites, apply reviewed edits to a preview, compute the plan ID | Propose `adaptations` from evidence; ask only unresolved team questions; iterate |
| 3. Apply | `apply_import` (stage 3) | Recheck every input, stage writes, write provenance, report partial failure | Show the result and invocation steps |

The `plan-import` skill drives steps 1–2 and states that apply is not available yet.

## Records

All records use project-relative POSIX paths. Absolute paths, usernames, and credentials never appear in tool output that is meant to be shared, plans, or provenance. Inputs remain absolute because the server needs them; outputs do not echo them.

- **Source identity:** `name` (explicit `source_name`, otherwise the sanitized `origin` remote URL with user info removed, otherwise the directory basename), optional repository subdirectory `path`, and optional Git `revision`. Git is queried only with `rev-parse` and `config --get`, with optional locks disabled; `status` is avoided because repository configuration can run commands during it. File hashes are the authority for uncommitted changes; revision is context.
- **Asset:** `{ key, kind, path }`. `kind` is one of `skill`, `command`, `rule`, `spec`, `doc`, `entry`. A skill is the directory containing `SKILL.md`; other kinds are single files. `key` is `kind:path`, portable across checkouts.
- **Bundle file:** `{ source, destination, role, hash, bytes, executable, text, alias_of? }`. `role` is `entry`, `support` (inside the skill directory), or `reference` (linked from bundle text, outside the directory). A file symlink inside the source root is copied as a regular file at its alias path, with `alias_of` naming the canonical file, so links to either path stay valid. A directory symlink to an already collected directory is listed under `aliases` and not copied twice.
- **Finding:** `{ code, severity, path?, detail }`. `severity: blocking` prevents `ready: true`. Codes: `missing_reference`, `outside_root`, `unsupported_file`, `too_large`, `bundle_limit`, `unsafe_destination`, `duplicate_destination`, `destination_conflict`, `possible_secret`, `machine_path`, `adaptation_not_found`, `adaptation_ambiguous`, `entry_file` (blocking); `dynamic_dependency`, `external_capability`, `client_binding_pending` (advisory). Advisory findings from model input are never mixed in; adaptations carry their own `reason`.
- **Plan:** `{ version: 1, plan_id, ready, source, destination, selection, files, adaptations, findings, adaptation_sites, preview }`. `plan_id` is the SHA-256 of the canonical JSON of source identity, every source hash, every destination state (`absent` or hash), mapping, resolutions, and adaptations. Apply (stage 3) recomputes the plan from the same request and rejects any difference.
- **Provenance (stage 3):** written to `.agents/adoptions/<source-name-slug>.json` in the destination: source identity, revision, per-file source hash, destination path, destination hash written, applied adaptations with reasons, and the plan ID. No timestamps-as-identity, no machine paths. Its location is configurable later; nothing else in the destination layout is required.

## Stage 1 — fixtures and contract (#2 scope, this change)

- Synthetic source project (TypeScript, pnpm) with a `release-notes` skill that has a referenced doc outside the skill directory, a script, a template, a config file, a symlink alias, an MCP capability mention, a pnpm command, and a machine path. Plus an unrelated skill that must stay unselected.

- The `manifest.yaml`/`sources.lock` names in #2 are not adopted. #2 is narrowed to the records above.
- Tests prove both tools leave both trees unchanged, including modes and link targets.

## Stage 2 — bundles and plan preview (#3, #4 scope, this change)

**Candidates.** Reuse the bounded discovery walk for the source root, group files under a `SKILL.md` directory into one skill (decided by the canonical path, so a skill first reached through a link stays a skill), and classify the rest by location (`commands/`, `rules/`, `specs/`, root `AGENTS.md`/`CLAUDE.md` as `entry`). Return description from YAML frontmatter (plain, quoted, continued, and `>`/`|` block scalars), file count, and size. A single-file candidate that mentions a skill directory lists it in `related`, which pairs command wrappers with their skills. Stack evidence for both projects comes from marker files (`package.json` + lockfile, `pyproject.toml`, `uv.lock`, `go.mod`, `Cargo.toml`, `build.gradle(.kts)`, `pom.xml`), `package.json` script names, and existing agent locations.

**Bundles.** For each selected asset, walk the skill directory with all file types (limits: 500 files per plan, 1 MiB per file, depth 16). Parse Markdown links, reference-style links, and `@path` imports in text files; resolve relative to the file. Fragments, URLs, and absolute paths are not followed. Referenced in-root files are added with role `reference` and parsed transitively, bounded by the same limits and a visited set. Missing targets and links leaving the source root are blocking until the user excludes them (`exclude`). Including out-of-root files is deferred; the finding says to move or exclude. Scripts are read as data; their imports are not analyzed and each script yields one `dynamic_dependency` advisory. `mcp__server__tool` mentions and `allowed-tools` frontmatter yield `external_capability` advisories.

**Destination mapping.** Defaults: `.claude/skills/X`, `.codex/skills/X`, `.cursor/skills/X` → `.agents/skills/X`; `.claude/commands/X` → `.agents/commands/X`; `.cursor/rules/X` → `.agents/rules/X`; `.agents/**` and every other path keep their relative location. `mappings` (`{ "source prefix": "destination prefix" }`, longest prefix wins) override defaults so destination layouts are preferred over `.agents/`. Root entry files (`AGENTS.md`, `CLAUDE.md`) are never written as destination entry files; they produce a blocking `entry_file` finding until mapped elsewhere.

**Reference rewriting.** When a referenced file's destination changes relative to the referencing file, rewrite that link target in the preview. Rewrites are deterministic and listed separately from model adaptations.

**Safety checks.** Destination paths must be relative, inside the destination after resolving existing parent symlinks, outside the source root, not themselves symlinks, not under `.git/`, and not under `.agents/local/`. Destinations are compared case-insensitively for duplicates. Two bundle files on one destination block. An existing destination with an identical result is `unchanged` (supports safe reapply); a differing one is `destination_conflict` until resolved with `resolutions: { "dest": "keep_destination" }` or a mapping change. Modification time never picks a winner.

**Data boundary checks.** Absolute home-like paths (`/Users/…`, `/home/…`, `C:\Users\…`) are `machine_path`; common token shapes (cloud keys, Git hosting and chat tokens, private key blocks, `password|secret|token|api_key = "…"`) are `possible_secret`. Both are blocking and are resolved by an adaptation that removes the value or by excluding the file. The plan states that detection is heuristic.

**Adaptations.** `adaptation_sites` lists deterministic evidence with file and line: source-only package-manager and toolchain commands found in code spans and scripts (for example `pnpm` when the destination uses `uv`), and inline-code paths that exist in the source but neither in the destination nor in the bundle. The client proposes `adaptations: [{ file, find, replace, reason }]` or whole-file rewrites `[{ file, content, reason }]` against source-relative paths. Each `find` must match exactly once (`adaptation_not_found` / `adaptation_ambiguous` otherwise). Adaptations apply when a file is collected, before its references are followed, so a link removed by an adaptation is not required and adaptation sites reflect the adapted text. A link that is absent from the source, or that appears in a whole-file rewrite, and resolves from the file's destination path to an existing destination file is a destination-owned reference: it is listed in `destination_references`, counted in the plan ID, and not copied. This lets an adapted workflow procedure link the destination's own rules instead of carrying the source's policy. The plan echoes a rewrite's `content_hash`, not its content; the diff preview shows the text. Procedure-order or approval changes are written as explicit adaptations with reasons, not hidden in bindings.

**Preview.** Per file: action (`create`, `unchanged`, `conflict`, `skip`), role, rewrites, adaptations, and a unified diff against the current destination (empty for absent files), capped at 400 lines per file with truncation reported. Binary files show hash and size only.

**Read-only proof.** Tests snapshot both fixture trees (paths, hashes, modes) before and after both tools.

## Stage 3 — safe application (#5)

- `apply_import` takes the same request as `plan_import` plus the reviewed `plan_id`, recomputes the plan, and refuses unless it is `ready` and the ID matches. This covers stale source, destination drift, and expected absence.
- Write to `.agents/local/import-staging/<plan_id>/` first, then rename into place file by file, rechecking each destination's expected state immediately before the rename. Never overwrite a file whose state changed.
- A journal (`.agents/local/import-state/<plan_id>.json`, untracked) records pending/committed files. On retry, committed files whose hash still matches are left alone; edited ones are preserved and reported; the plan is reported complete only when every file is committed and provenance is written last.
- Reapplying a completed plan finds every file `unchanged` and writes nothing. A new import of edited files yields conflicts, not updates.
- Preserve the executable bit on POSIX. No script execution, hook registration, commit, push, or global configuration change.

## Stage 4 — client entry points (#7)

- Codex reads `.agents/skills` directly; generate nothing when skills land there. Claude Code reads `.claude/skills`; generate a thin `SKILL.md` wrapper that keeps the frontmatter and points to the `.agents` file instead of a symlink (portable on Windows).
- Never modify existing `CLAUDE.md`/`AGENTS.md`; preview a suggested addition for the user to apply.
- Until this stage exists, plans carry `client_binding_pending` and are not described as usable in a client.

## Stage 5 — independent use (#9)

Clone the destination fixture into a second directory without the source or Agent Weave, run reference validation, and manually invoke the procedure in Claude Code and Codex. Record client version, OS, working directory, and settings, separate from fixture tests.

## Explicitly out of scope here

Pack descriptors, Git acquisition, out-of-root inclusion, baselines and three-way updates, rollback, Cursor/VS Code adoption adapters, `resolve_context` (#6), standalone doctor (#8).
